# Test Results

One report per backtest run of `scripts/backtest_signals.py`, each with a **Setup** section (exact command, symbol/window, strategy configuration, evaluation method) and a **Findings** section (what the numbers mean, not just what they are). Raw per-signal CSVs referenced by these reports live under `backtest_results/` (gitignored, local only) — reports summarize and interpret them, not replace them.

All runs so far were made against real MT5 historical data (`MetaQuotes-Demo`, EURUSD) via `pipenv run python scripts/backtest_signals.py`, no real orders placed.

**Headline result**: [zero-spread-retune.md](zero-spread-retune.md) — the user confirmed the trading account's real spread is genuinely near-zero (not a pessimistic assumption). Re-tuning under that condition **completely changes the picture: every ratio from 3:5 to 10:5 clears breakeven for MTF, peaking at 8:5 with a +9.2 point margin (window 1) / +5.9 (window 2, out-of-sample)** — a real, comfortable margin instead of the earlier "right at breakeven" result. `Config.DEFAULT_TP_PIPS` updated from 7.0 to 8.0 to match. Single-timeframe also improved (peak +4.3 at 4:5) but stays clearly behind MTF.

**Also tried and rejected**: [ml-entry-model-comparison.md](ml-entry-model-comparison.md) — a RandomForest trained on the same indicators lost to the hand-coded rules in all 4 window/strategy combinations tested (single-tf: -1.8 to -6.3 points; MTF: -9.8 to -18.9 points). `Config.USE_ML_ENTRY_MODEL` stays `False`; the infrastructure remains for future iteration with different features/labels/models.

**Also tried and rejected**: [ntick-confirmation-backtest.md](ntick-confirmation-backtest.md) — n-tick confirmation looked like a clear win in window 1 (every N beat baseline, improving with N) but flatly reversed in window 2 (underperformed baseline, below breakeven) — doesn't survive an out-of-sample check, confirmed against both a manual correction and the real fix below. `Config.N_TICK_CONFIRMATION` stays `1`. Also surfaced and **fixed** a real bug along the way: confirmed signals were bypassing the session filter entirely (`SignalOrchestrator` calls `get_confirmed_signal()` directly, which `SessionFilteredSignalStrategy` didn't gate) — `get_confirmed_signal` now takes the confirming tick's time and vetoes during blocked hours, same as `generate_signal` already did.

**First full exit-strategy-aware result**: [pre-breakeven-exit-strategy-backtest.md](pre-breakeven-exit-strategy-backtest.md) — every report above evaluates signal quality via a fixed target/stop proxy, not real trade lifecycles. This one feeds real entries through the real, production `LossExitManager` against real historical ticks. Finding: 90.6%-97.4% of trades reach breakeven almost immediately (avg 3-7 ticks) — a direct consequence of this account's near-zero spread — so the pre-breakeven soft SL we just wired (`EXIT_MAX_LOSS_MONEY=5.0`) barely ever fires (1.3%-1.7% of trades). Highly consistent across both windows, unlike the entry-signal win rates. **Counterfactual follow-up** (`--counterfactual`, scaled to 7 majors x 3 windows after a small first pass): replaying the same real ticks as if only the broker-side wide SL existed, on a real sample (585 cut-short trades), shows the pre-breakeven soft SL/timeout is a modest **net positive** — real P&L -$1,532.67 vs counterfactual -$1,616.89 (+$84.23, early cuts helped). Reverses the original small-sample (17-trade) finding, which had pointed the other way — a useful lesson in trusting sample size over an initial direction. Scaling up the sweep also surfaced and fixed a real bug: profit for USD-base pairs (USDJPY/USDCHF/USDCAD) was computed in the wrong currency, inflating USDJPY's numbers by ~150x before the fix. Still says nothing about post-breakeven profitability (the trailing logic is separately known to be hardcoded, untested here).
